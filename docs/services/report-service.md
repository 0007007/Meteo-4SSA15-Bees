report-service is the 7th microservice, written in Python with FastAPI. It owns report requests and recurring report schedules, and it is the only service that reads the others: it collects a city's data through the gateway and writes a CSV or PDF file.

## At a glance

| Item | Value |
| --- | --- |
| Owner | Team (to assign) |
| Entities | ReportSchedule and Report |
| Stack | Python 3.11+, FastAPI, SQLAlchemy 2, Pydantic 2, requests, reportlab, py-eureka-client, uvicorn |
| Port | 8087 (clients use the gateway on 8090) |
| Database | PostgreSQL, schema `report_db` |
| Eureka name | `report-service`, registered by py-eureka-client |
| REST resources | `/api/report-schedules`, `/api/reports` |
| API docs | Swagger UI generated by FastAPI at `http://localhost:8087/docs` |

## Entities

Both entities are SQLAlchemy models in `app/models.py`; the JSON bodies are Pydantic schemas in `app/schemas.py`, in camelCase like the Java services.

### ReportSchedule

Stored in table `report_schedules`. REST resource `/api/report-schedules`.

| Field | Type | Required | Rules |
| --- | --- | --- | --- |
| id | integer | auto | generated by the database |
| name | string | yes | 1 to 100 characters |
| cityId | integer | yes | > 0; id of a City in geo-service, not checked |
| reportType | ReportType | yes | one of SUMMARY, OBSERVATIONS, FORECASTS, ALERTS |
| format | ReportFormat | no | one of CSV, PDF; default PDF |
| frequency | Frequency | yes | one of DAILY, WEEKLY, MONTHLY |
| recipientEmail | string | no | valid email address; max 120 characters |
| active | boolean | no | default true |
| createdAt | date-time | auto | set by the server at creation |

### Report

Stored in table `reports`. REST resource `/api/reports`.

| Field | Type | Required | Rules |
| --- | --- | --- | --- |
| id | integer | auto | generated by the database |
| title | string | yes | 1 to 150 characters |
| cityId | integer | yes | > 0; id of a City in geo-service, checked only at generation |
| reportType | ReportType | yes | one of SUMMARY, OBSERVATIONS, FORECASTS, ALERTS |
| format | ReportFormat | no | one of CSV, PDF; default PDF |
| periodStart | date | yes | — |
| periodEnd | date | yes | on or after periodStart |
| scheduleId | integer | no | id of an existing ReportSchedule; foreign key `schedule_id` |
| status | ReportStatus | auto | PENDING, GENERATED or FAILED; set by the server |
| fileName | string | auto | name of the generated file |
| errorMessage | string | auto | reason of the last failed generation |
| createdAt | date-time | auto | set by the server at creation |
| generatedAt | date-time | auto | time of the last successful generation |

What each report type contains:

| reportType | Content of the file |
| --- | --- |
| SUMMARY | one row per indicator: stations, observations, min / average / max temperature, average humidity, total rain, max wind, average air quality index, forecast days, alerts in total and by severity |
| OBSERVATIONS | one row per observation of every station of the city during the period |
| FORECASTS | one row per forecast day inside the period |
| ALERTS | one row per alert that overlaps the period |

## REST API

Through the gateway: `http://localhost:8090`. Direct, for debugging: `http://localhost:8087`.

| Method | Path | Action | Success | Errors |
| --- | --- | --- | --- | --- |
| GET | `/api/report-schedules` | list all; `?cityId=` filters | 200 | — |
| GET | `/api/report-schedules/{id}` | get one ReportSchedule | 200 | 404 |
| POST | `/api/report-schedules` | create | 201 | 400 |
| PUT | `/api/report-schedules/{id}` | replace | 200 | 400, 404 |
| DELETE | `/api/report-schedules/{id}` | delete | 204 | 404, 409 |
| POST | `/api/report-schedules/{id}/run` | create and generate the report of the last 1, 7 or 30 days | 201 | 404, 409 |
| GET | `/api/reports` | list all; `?cityId=` filters | 200 | — |
| GET | `/api/reports/{id}` | get one Report | 200 | 404 |
| POST | `/api/reports` | create, with status PENDING | 201 | 400, 404 |
| PUT | `/api/reports/{id}` | replace; back to PENDING, old file removed | 200 | 400, 404 |
| DELETE | `/api/reports/{id}` | delete the report and its file | 204 | 404 |
| POST | `/api/reports/{id}/generate` | collect the data and write the file | 200 | 404 |
| GET | `/api/reports/{id}/download` | download the file (`text/csv` or `application/pdf`) | 200 | 404, 409 |
| GET | `/health` | health check used by Eureka | 200 | — |

Example: create a Report with `POST /api/reports`

```json
{
  "title": "Tunis - observations",
  "cityId": 1,
  "reportType": "OBSERVATIONS",
  "format": "PDF",
  "periodStart": "2026-11-01",
  "periodEnd": "2026-11-30",
  "scheduleId": null
}
```

Response `201 Created`:

```json
{
  "title": "Tunis - observations",
  "cityId": 1,
  "reportType": "OBSERVATIONS",
  "format": "PDF",
  "periodStart": "2026-11-01",
  "periodEnd": "2026-11-30",
  "scheduleId": null,
  "id": 1,
  "status": "PENDING",
  "fileName": null,
  "errorMessage": null,
  "createdAt": "2026-11-11T09:20:11.412305",
  "generatedAt": null
}
```

Then `POST /api/reports/1/generate` returns the same report with `"status": "GENERATED"`, `"fileName": "report-1-observations.pdf"` and a `generatedAt` time. If a service it reads is stopped, the call still returns 200 with `"status": "FAILED"` and the reason, for example `"errorMessage": "/api/stations returned HTTP 503"`.

Example: create a ReportSchedule with `POST /api/report-schedules`

```json
{
  "name": "Weekly summary - Tunis",
  "cityId": 1,
  "reportType": "SUMMARY",
  "format": "PDF",
  "frequency": "WEEKLY",
  "recipientEmail": "team@example.com",
  "active": true
}
```

`POST /api/report-schedules/1/run` then creates and generates a Report titled "Weekly summary - Tunis (2026-11-05 to 2026-11-11)" covering the last 7 days, linked with `"scheduleId": 1`.

## How a report is generated

1. The service reads the Report: city, type, format and period.
2. It calls the gateway (`GATEWAY_URL`): `GET /api/cities/{cityId}` always; `/api/stations?cityId=` then `/api/observations?stationId=` for each station (OBSERVATIONS, SUMMARY); `/api/air-quality?cityId=` (SUMMARY); `/api/forecasts?cityId=` (FORECASTS, SUMMARY); `/api/alerts?cityId=` (ALERTS, SUMMARY).
3. It keeps the records dated inside the period; alerts are kept when they overlap it.
4. It writes `generated-reports/report-{id}-{type}.csv` or `.pdf`. The CSV is a header row plus data rows in UTF-8 with BOM, so Excel shows °C correctly. The PDF is an A4 table with title, city and period; observations and alerts use landscape pages.
5. It saves the status GENERATED with `fileName` and `generatedAt`, or FAILED with `errorMessage`.

## Rules and errors

- Every POST and PUT body is validated by Pydantic; a broken rule returns 400 with the field list, in the same JSON shape as the Java services.
- `periodEnd` before `periodStart` returns 400.
- `scheduleId` must point to an existing ReportSchedule; otherwise 404.
- A ReportSchedule that still has reports cannot be deleted: 409. Delete its reports first.
- "Run now" on an inactive schedule returns 409.
- Downloading a report that has no file yet returns 409, with a message saying to call `generate` first.
- Generation does not fail the HTTP call when another service is down: the report is saved as FAILED with the reason, so the client can show it.
- `cityId` is not checked on create; an unknown city makes the generation fail with "/api/cities/{id} returned 404 (not found)".
- At startup the service creates `report_db` if it is missing, then its two tables (SQLAlchemy `create_all`).

## Links with other services

This service points to:

- Report.cityId and ReportSchedule.cityId → City in geo-service

It reads, at generation time and through the gateway:

- geo-service: the city and its country
- station-service: the stations of the city
- observation-service: observations and air quality
- forecast-service: forecasts
- alert-service: alerts

The Angular frontend uses it on the Reports and Report schedules pages (Generate, Download, Run now).

## Configuration

All settings are environment variables read in `app/config.py` (the Python equivalent of `application.yml`); `.env.example` lists them.

| Variable | Default | Used for |
| --- | --- | --- |
| PORT | 8087 | HTTP port |
| DATABASE_URL | postgresql+psycopg://meteo:meteo@localhost:5432/report_db | SQLAlchemy connection |
| GATEWAY_URL | http://localhost:8090 | where the data of the other services is read |
| EUREKA_URL | http://localhost:8761/eureka/ | registry address |
| EUREKA_ENABLED | true | set to false to run without Eureka |
| INSTANCE_HOST | localhost | host name registered in Eureka |
| INSTANCE_IP | 127.0.0.1 | IP registered in Eureka |
| REPORTS_DIR | generated-reports | folder of the generated files |
| APP_NAME | report-service | name registered in Eureka |

If the Eureka registration fails, the service still answers on 8087; the gateway route can then point to `http://localhost:8087` instead of `lb://report-service`.

## Code structure

The layers match the Java services: routers = controllers, services = services, repositories = repositories, models = entities.

```
report-service/
├── app/
│   ├── clients/
│   │   └── meteo_client.py         calls the other services through the gateway
│   ├── exports/
│   │   ├── content.py              builds the table of each report type
│   │   └── writers.py              writes CSV (csv) and PDF (reportlab)
│   ├── repositories/
│   │   ├── report_repository.py
│   │   └── schedule_repository.py
│   ├── routers/
│   │   ├── report_router.py        /api/reports
│   │   └── schedule_router.py      /api/report-schedules
│   ├── services/
│   │   ├── report_service.py       create, update, generate, download
│   │   └── schedule_service.py     create, update, run now
│   ├── config.py                   environment variables
│   ├── database.py                 engine, session, database creation
│   ├── exceptions.py               404 / 400 / 409 as JSON
│   ├── main.py                     FastAPI app, Eureka registration
│   ├── models.py                   Report, ReportSchedule, enums
│   └── schemas.py                  request and response bodies
├── .env.example
└── requirements.txt
```

## Run and test

1. Install Python 3.11 or newer. In `report-service/`, run `python -m venv .venv`, activate it (`.venv\Scripts\activate` on Windows, `source .venv/bin/activate` elsewhere), then `pip install -r requirements.txt`.
2. Start PostgreSQL (`docker compose up -d` at the project root) and discovery-server, then run `python -m app.main`.
3. Check `http://localhost:8087/health` returns `{"status":"UP"}`, that `REPORT-SERVICE` appears on the Eureka dashboard, and try the endpoints in `http://localhost:8087/docs`.
4. Through the gateway: create a report, call `generate`, then `download`; or run the Postman folders "report-service (Python) / ReportSchedule" and "report-service (Python) / Report".
